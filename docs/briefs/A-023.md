## 2. Design decisions PLAN.md already owns for this artifact (§4 A-023, recorded before the toolchain was installed)

- **The Unity gate is closed by installing, not by claiming.** A-023 stays `proposed`
  until an editor and the build modules are actually on disk and run.
- **Version choice: Unity 6 LTS `6000.0.84f1`.** The promoted list also offers
  `7000.0.0a8` (alpha), `6000.7.0b4` (beta), `6000.6.5f1`, `6000.3.26f1`. A shipping
  mobile target sits on the LTS so the toolchain cannot drift mid-project; betas,
  alphas, and point releases are rejected. Do not re-pick the version.
- **Build modules `ios android` with child modules** (`android-sdk-ndk-tools`,
  `android-open-jdk`) — A-014 names iOS and Android device classes, so the editor
  alone is not enough. `install-modules` is the documented way to add them.

## 3. The design rule (PLAN.md §8) and the phase boundary

- Phase 1 (A-021) and Phase 2 (A-022) are merged and green: the deterministic fixed-point
  core, the harness, the frame driver. A-023 is the **player-facing** package: it renders
  and ships; it never re-implements the simulation.
- `DT` stays `71582788L` (1/60). Time scale is the weak-device fallback (A-014 P-02),
  never `DT`.
- Monetization never blocks completion of the core game (PLAN hard rule).
- The renderer reads `SimState` and never writes to it (A-026 states this contract;
  A-005 §5.2 repeats it: "RenderLayer is strictly read-only against sim state").

## 4. Architecture excerpts you must honor (PLAN.md §5 / docs/architecture.md module tree)

```text
 ├─ RenderLayer          interpolation, LOD, culling, particles, horizon ring
 ├─ InputAdapter         Unity Input System -> per-step intent (mapping: A-011)
 ├─ UIRoot               HUD and menus (A-010)
 └─ PlatformBridge       Unity Ads / IAP, analytics, crash reporting (A-015..A-017)
```

Data flow: `InputAdapter -> intent` → sim; `RenderLayer.read(SimCore state, alpha)`.
RenderLayer exposes a `visibilityLayer` output (edge indicators) — a hook, not a sim write.

## 5. The frame clock you already have (A-022, merged)

`FrameDriver.frame(clock, state, digest)` owns per-run frame state (frame index, hitch
schedule, tier) in a `FrameClock` object — never static globals. `FixedStepDriver.advanceDigest`
is the per-step intent entry point sharing ONE accumulator/catch-up/dropped-step
implementation. The non-Unity client (A-026) reaches the same driver; A-023 must too.

## 6. Device classes and the gates A-014 names (docs/qa.md §, quoted)

| Class | Definition | Gates it must satisfy |
| --- | --- | --- |
| Modern phone | Mid-range Android (2023–2025 class, ≥8 GB RAM, 60 Hz+ display) plus one current-gen iOS device | P-01 60 fps (p95 frame ≤ 16.6 ms, no hitch > 50 ms), P-03 no shader spikes, P-08 draw calls, I-02 drag on largest frame |
| Weak device | Oldest still-shippable Android (≤2 GB RAM, throttled CPU) | P-02 30 fps fallback via time scale (never `DT`), P-04 flat memory (RSS max−min ≤ 2 MB after warm-up), P-05 steady state allocates from pools only (per-frame allocation counters read 0 after warm-up) |

A-023 produces the **candidate** build for these classes. P-01/P-02/P-04/P-05 need real
hardware; they are not greenable by building. Record what the build makes measurable,
never claim a gate green without a run on the named class.
